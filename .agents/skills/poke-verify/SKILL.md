# 요구사항 기반 검증

[AGENTS](../../../AGENTS.md)를 따르고 현재 diff와 대상 요구사항을 확인한다.
검증 범위는 [QA](../../../docs/QA.md)의 관련 절, 실행 방법은 필요할 때 [HARNESS](../../../docs/HARNESS.md)를 읽는다.
새 브랜치 없이 검증할 수 있다. 기존 결과는 [STATUS](../../../docs/STATUS.md)의 환경·대상 변경과 대조한다.

1. Node/npm과 의존성 상태를 확인한다. 설치가 필요하면 lockfile 기준 npm ci를 사용한다.
   도구 미설치·네트워크 실패·브라우저 엔진 부재는 코드 테스트 실패와 분리한다.
2. 변경에 맞춰 검증한다. 판정은 699/700·비명중·저파워 및 좌표 fixture,
   입력은 해제·repeat·멀티터치, 수명은 중지·스킵·오래된 콜백,
   저장은 손상·미래 스키마·재도전 시 유지가 중요한 회귀다.
3. npm run check 후 UI/통합 변경에는 npm run test:e2e를 실행한다.
   E2E는 dist를 사용하므로 빌드 실패 상태에서 오래된 dist 결과를 증거로 쓰지 않는다.
4. 이번 요청이 실기기·성능·출시 검증이면 QA의 해당 게이트를 별도로 수행한다.
   환경이 없으면 미실행으로 기록한다. WebKit/모바일 에뮬레이션은 실제 iPhone 측정이 아니다.
5. 필수 검사 통과 후 새 변경·실패·미해결 우려가 없으면 동일 검사를 반복하거나 범위를 확대하지 않는다.
6. [검증 양식](../../../docs/templates/VERIFICATION.md)의 날짜·기준 커밋 또는 작업 트리·명령·결과·제약을 남긴다.
   requirements evidence는 실제 파일을 가리키게 하고 STATUS에 실제 결과를 요약한다.

read-only 리뷰 요청이면 파일을 수정하거나 요구사항 상태를 올리지 않고 결과만 보고한다.
하니스 계획 무결성은 캐릭터 완성·연출 품질·재미를 증명하지 않는다.
