# 프로젝트 문서 지도

## 기준과 이번 범위

사용자 요청: 새 앱의 마크다운을 기반으로 필요한 문서와 하니스를 구성한다.
이번 산출물은 M0 개발 준비이며, 원본의 “실행 가능한 전체 게임을 제작하라”를 이번 턴의 추가 구현 요청으로 해석하지 않는다.
원본의 제품 요구사항은 후속 개발의 수용 기준으로 추출했다.

우선순위는 현재 사용자의 명시적 결정 → 확인된 프로젝트 결정 → 원본 제품 요구사항 → 파생 설계다.
해석 차이는 decisions/0001-project-baseline.md에 남기며, 원본을 수정하지 않는다.
새 기술 수치와 일정 추정은 확정 규칙과 구분한다.

| 파일 | 관리할 내용 | 갱신 시점 |
|---|---|---|
| PRODUCT.md | 사용자 경험, 범위, 금지 기능, 화면·접근성 | 제품 결정 변경 |
| GAME_RULES.md | 점수, 실패 우선순위, 입력·시간·판정 계약 | 규칙·설정 변경 |
| ARCHITECTURE.md | 상태, 책임, 저장, 재현, 복구 | 구조·데이터 변경 |
| CONTENT.md | 8개 캐릭터, 5계열, 연출·에셋 제작 기준 | 콘텐츠 추가·검수 |
| content-plan.json | 제작할 캐릭터·결말 조합의 기계 검사 자료 | 조합 변경 |
| requirements.json | 요구사항 ID, 원본 절, 담당 모듈, 검증, 증거 | 구현·검증 완료 |
| IMPLEMENTATION.md | 의존 순서와 각 단계의 종료 조건 | 단계 완료 |
| QA.md | 자동·수동·실기기·플레이 테스트, 출시 게이트 | 검증 계획 변경 |
| HARNESS.md | 명령, fixture, CI, 오류 진단 | 도구 변경 |
| STATUS.md | 실제 수행 결과와 현재 한계 | 작업 종료 |
| templates/ | 작업, 검증, 플레이 테스트 기록 양식 | 후속 작업에서 복사 |

requirements.json의 status:

- planned: 요구사항·검증 계획만 있음.
- reference-tested: 일부 순수 로직에 기준 구현과 테스트가 있음. 제품 통합 완료가 아님.
- implemented: 제품에 연결했으며 수동 또는 자동 검증 증거가 있음.
- verified: 해당 요구사항의 전체 수용 기준과 지정 환경 검증을 마쳤음.

하니스 파일 존재 검사는 제품 완료 여부를 자동으로 올리지 않는다.
